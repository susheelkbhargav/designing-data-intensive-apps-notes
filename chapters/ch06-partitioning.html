1. Core Idea

Replication (Ch 5) copies data; partitioning splits it. When a dataset or query load is too big for one machine, break it into partitions (a.k.a. shards in MongoDB/Elasticsearch, regions in HBase, tablets in BigTable, vnodes in Cassandra/Riak) so each record belongs to exactly one partition, and spread partitions across nodes in a shared-nothing cluster.

📊 Scale data volume

No single disk holds the whole dataset.

⚡ Scale query throughput

Parallelize reads/writes across nodes.

⚖️ Fair load

Each node does roughly equal work — when partitioning works.

The whole game is spreading data and load evenly. Unfair partitioning is called skew; a partition with disproportionately high load is a hot spot — in the worst case one node does all the work while nine sit idle.
Partitioning + replication: usually combined — each node leads some partitions, follows others. But the two choices are mostly independent. Interview move: "Each shard has its own leader + followers" (Ch 5).

2. Framework: Partitioning by Key Range

Also: range sharding, encyclopedia volumes. BigTable, HBase, RethinkDB, early MongoDB.

WhenYou need efficient range scans (time-series reads, prefix lookups) and can tolerate hot-spot risk.
HowAssign each partition a contiguous range of sorted keys. Boundaries adapt to data density, chosen manually or automatically. Keys stay sorted within a partition (SSTable-style), so range queries hit one or few partitions.
Why it worksSort order is preserved — the key doubles as a concatenated index.
Failure modeAccess pattern concentrates on one end of the range: a timestamp key means all of today's writes land on today's partition while the rest idle.
📚 Encyclopedia shelf: volumes sorted A–Z — easy to find a chapter by letter. But if everyone only reads the newest volume, that shelf sags while the rest collect dust.

3. Framework: Partitioning by Hash of Key

Default for write-heavy key-value workloads. MongoDB (hash mode), Riak, Couchbase, Voldemort, Cassandra.

WhenEven distribution matters more than range queries.
HowHash each key (MD5/FNV — doesn't need to be cryptographic), assign each partition a range of hashes. Similar keys get scattered uniformly.
Why it worksA good hash turns skewed inputs into a uniform distribution.
Failure mode(a) Range queries — adjacent keys scattered, MongoDB hash mode sends range queries to all partitions; Riak/Couchbase/Voldemort don't support them on primary key. (b) Single hot key — identical keys → identical hashes → one partition hammered.
Consistent hashing caveat: Karger et al.'s consistent hashing (pseudo-random boundaries, built for CDN caches) rebalances poorly for databases — Cassandra abandoned it pre-1.2. "Consistent" here has nothing to do with replica or ACID consistency. Kleppmann's advice: avoid the term; say hash partitioning.

4. Skew, Hot Spots & Key Salting

Skew = uneven load defeats partitioning. Hashing reduces but can't eliminate it — for a single hot key the application must intervene.

ProblemExampleWhy hashing fails
Monotonic keys + range partitioningTimestamp as sole keyAll writes hit newest partition
Single celebrity / viral keyOne user ID gets all traffichash(same key) = same partition every time

Application-level fix: key salting

Append a 2-digit random suffix to spread writes over 100 keys (e.g. celebrity_id#42). Cost: reads must gather all 100 variants; you must track which keys are split.

🚨 Hot key on hash partition: A celebrity's ID still hammers one partition. No partition scheme fixes a single logical key — only the application can split it (salting) or cache aggressively at the edge.

5. Compound Primary Key

Cassandra-style: hash only the first column to pick the partition; remaining columns are a concatenated sort index within it.

(user_id, update_timestamp)
  ↑ hash this → pick partition
              ↑ sort within partition → cheap per-user time-range scans

Even distribution

Hash user_id → writes spread across users.

Efficient range scans

Within one partition, rows sorted by timestamp.

Scoped trade-off

Multi-user time-range query = N targeted scans (one per user), not one global scan.

Interview move: split "which partition" from "sort within partition." Hash the first component, sort by the rest. Used in chat systems (channel_id, message_id), email (user_id, …).

6. Secondary Indexes: Local vs Global

Primary key picks the partition. Secondary indexes let you query by non-primary fields — but partitioning forces a painful trade.

TypeAlso calledWritesReadsSystems
Document-partitioned Local secondary index Fast — touch one partition only Scatter/gather across all partitions — tail latency amplification MongoDB, Riak, Cassandra, Elasticsearch, SolrCloud, VoltDB
Term-partitioned Global secondary index Single doc update may touch many index partitions → typically async (DynamoDB GSIs) Fast — read hits one partition DynamoDB GSIs
Pick your pain: write-cheap / read-expensive (local index) or read-cheap / write-expensive (global index). Secondary indexes force this trade — there is no free option. Synchronous global index updates need distributed transactions (Ch 7 & 9) — which is why DynamoDB GSIs are async.

7. Rebalancing Strategies

Moving data between nodes as load or cluster size changes. Requirements: fair load after, keep serving reads/writes during, move no more data than necessary.

🚨 hash mod N (anti-pattern): hash(key) mod N reassigns most keys whenever N changes — rebalancing becomes catastrophically expensive. Never use this.
StrategyHowBest forCaveat
Fixed number of partitions Create far more partitions than nodes (e.g. 1,000 for 10 nodes); new nodes steal whole partitions. Key→partition mapping never changes, only partition→node. Hash partitioning Riak, Cassandra ≥1.2, Elasticsearch, Couchbase
Dynamic partitioning Split when partition exceeds size threshold (HBase default 10 GB), merge when it shrinks — B-tree-like. Count adapts to data volume. Key-range partitioning Empty DB starts with one partition (one busy node) — mitigate with pre-splitting
Fully automatic rebalancing + automatic failure detection: a slow node gets declared dead, rebalancing dumps its load on the rest, overloading them → cascading failure. Couchbase/Riak/Voldemort keep a human commit step for this reason.

8. Request Routing & Coordination

Service discovery: how does a client find the right node for a key?

1
Any-node routing — client hits any node, which forwards to the partition owner
2
Routing tier — partition-aware proxy (mongos, moxi) sits between clients and storage nodes
3
Partition-aware clients — client library knows the partition map directly

The hard part: keeping everyone's view of partition → node assignment in agreement.

Coordination approachSystemsTrade-off
ZooKeeper (or Helix)HBase, SolrCloud, Kafka; Espresso via HelixExternal dependency; authoritative partition map
GossipCassandra, RiakNo external dependency; more node-side complexity
Node IPs change slowly enough that DNS suffices for the network layer. The partition map itself lives in coordination (ZooKeeper-like) or gossip — and everyone must agree (Ch 9 consensus territory for strong guarantees).

9. Mental Models

1. Each partition is a small DB

Independence is what makes scaling linear. Anything crossing partitions (global indexes, multi-key writes) is where the pain lives.

2. Encyclopedia shelf

Key-range = sorted volumes — easy to find, but uneven unless boundaries follow the data.

3. Move the mapping, not the data

Fixed partitions and dynamic splits change partition→node only. Hash mod N entangles both mappings — catastrophic on resize.

4. Pick your pain on indexes

Local index: write-cheap, read-expensive. Global index: read-cheap, write-expensive (usually async). No free lunch.

11. Worked Example: Sensor Network Compound Key

Sensor network storing measurements. Key = measurement timestamp (year-month-day-hour-minute-second).

Attempt 1: Key-range partitioning

Keys sorted → "all readings for March" is one cheap range scan. But writes arrive in real time — every insert lands in today's partition. One node saturates on writes; the rest idle. Classic hot spot from a monotonically increasing key.

Attempt 2: Hash partitioning

Hash the timestamp → writes spread uniformly. But sort order is gone: "all readings from 17:08:10 to 17:09:00" must query every partition (scatter/gather).

Attempt 3: Compound-key fix (Cassandra-style)

Primary key = (sensor_name, timestamp)
              ↑ hash → partition     ↑ sort within partition

With many concurrent sensors, write load spreads evenly. Per-sensor time-range queries are single-partition and efficient. Cost: multi-sensor time-range query = one range query per sensor name — you've traded a global scan for N targeted scans (fine when N is bounded).

Interview move: identify the hot key structure, split "which partition" from "sort within partition." Don't accept the false binary of range-vs-hash — compound keys buy both, scoped.

14. Key Takeaways

  1. Key-range gives cheap range scans but risks hot spots; hash gives even load but kills range queries. Compound keys buy both, scoped: hash the first component, sort by the rest.
  2. Hashing can't fix a single hot key — that's application-level (key salting), with read-side gather cost.
  3. Local secondary indexes: fast writes, scatter/gather reads. Global (term-partitioned): fast reads, multi-partition (usually async) writes.
  4. Rebalance by moving whole partitions: fixed-count for hash partitioning, dynamic split/merge for key ranges. Never hash mod N.
  5. Routing is service discovery; the authoritative partition map lives in ZooKeeper-like coordination or gossip, and everyone must agree.
  6. Keep a human in the loop for rebalancing — automation plus failure detection can cascade.

15. Junior SWE Checkpoints

Q1: What's the difference between replication and partitioning?

Replication copies the same data to multiple nodes (availability, read scaling). Partitioning splits data so each record lives on exactly one partition (data volume + write/query scaling). Usually combined: each node leads some partitions, follows others.

Q2: Why is timestamp-as-primary-key bad for key-range partitioning?

Timestamps are monotonically increasing — all new writes land on the newest partition (today's range). One node saturates; rest idle. Classic hot spot. Fix: compound key (hash entity ID, sort by timestamp) or hash the timestamp if range scans aren't needed.

Q3: Hash partitioning spreads load but breaks what?

Range queries on the primary key. Adjacent keys scatter to different partitions — "user:40 to user:50" must query all partitions (scatter/gather). Hash also can't fix a single hot key (celebrity ID) — same hash every time.

Q4: Explain compound key (user_id, timestamp) in one sentence.

Hash user_id to pick the partition (even spread across users); sort by timestamp within the partition (cheap per-user time-range scans).

Q5: Local vs global secondary index — what's the trade?

Local (document-partitioned): write touches one partition; read scatter/gathers all partitions. Global (term-partitioned): read hits one partition; write may fan out to many index partitions → typically async (DynamoDB GSIs).

Q6: Why is hash(key) mod N an anti-pattern?

When N (node count) changes, nearly every key's partition assignment changes — catastrophic rebalancing. Fixed partition count (move partition→node only) or dynamic split/merge avoids this.

Q7: Sensor network — walk through the three partitioning attempts.

(1) Key-range on timestamp: cheap range scans, write hot spot on today's partition. (2) Hash timestamp: even writes, no cheap range scans. (3) Compound (sensor_name, timestamp): hash sensor for even writes, sort by timestamp for per-sensor range queries. Multi-sensor global query = N targeted scans.
