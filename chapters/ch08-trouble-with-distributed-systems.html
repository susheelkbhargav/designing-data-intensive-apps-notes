1. Core Idea

A single computer is deterministic: it works or it crashes, never something in between. A distributed system loses that idealization — you get partial failures that are non-deterministic.

🌐 Unreliable network

Packets lost, duplicated, reordered, or arbitrarily delayed.

🕐 Unreliable clocks

Out of sync, jumping forward or backward (NTP, leap seconds).

⏸️ Unreliable processes

Paused at any point for arbitrary lengths (GC, VM suspend, paging).

Reliability must be engineered on top of unreliable components — like TCP over IP. Make assumptions explicit via a system model, then design algorithms proven correct within it. A node cannot trust its own judgment; truth is a quorum decision (Ch 9).

2. Framework: System Models

Formalize what an algorithm may assume: timing × node failure. State your model before claiming any algorithm is correct.

Timing models

ModelAssumptionReality
Synchronous Bounded network delay, bounded process pauses, bounded clock error Unrealistic for practical internet-scale systems
Partially synchronous Behaves synchronously most of the time, but bounds are occasionally shattered arbitrarily The realistic model — most real server-side systems
Asynchronous No timing assumptions at all — not even a clock or timeouts Very restrictive; few algorithms work here

Node failure models

ModelBehaviorWhen to use
Crash-stop Failed node never returns Simplified analysis; rarely exact in production
Crash-recovery Nodes crash and may return; stable storage survives, in-memory state lost Default for real systems — partially synchronous + crash-recovery
Byzantine Nodes may do anything, including lying and sending corrupted messages Aerospace, blockchain, mutually untrusting orgs
When to use: State your model before claiming correctness. Most real server-side systems: partially synchronous with crash-recovery faults. Failure mode: reality leaks — disks corrupt, firmware bugs lose data, silently breaking algorithms that assume nodes remember what they stored.

3. Safety vs Liveness

Define algorithm correctness precisely by splitting properties into two categories.

PropertyMeaningExamplesRequirement
Safety "Nothing bad happens" — if violated, you can point at the exact moment it broke, and damage cannot be undone Fencing-token uniqueness, monotonic sequence; no split-brain writes Must hold always, even if all nodes crash or network fails entirely
Liveness "Something good eventually happens" — may not hold now, but hope remains ("eventually" is the giveaway) Availability; eventual consistency; "a response will arrive if majority is up" Conditional — e.g., only if majority is up and network eventually recovers
Eventual consistency is a liveness property — "eventually" all replicas converge. Safety properties (no lost acknowledged writes, no duplicate primary keys) must never be violated, even during partitions.

4. Unbounded Delays & Timeouts

Asynchronous packet networks give no delivery-time guarantee. No response is indistinguishable among many causes.

Possible causeWhat actually happened
Request lostPacket dropped in transit
Request queuedSwitch or server backlog
Remote node crashedProcess dead
Node paused (GC)Process alive but frozen — looks dead from outside
Response lostServer processed, reply never arrived
Response delayedStill in flight, will arrive late
No "correct" timeout exists. Too-short timeouts falsely declare live nodes dead → load shifts → cascading failure. Measure round-trip distributions and jitter, or adapt continuously (Phi Accrual failure detector, used in Akka and Cassandra).
📞 Calling someone who doesn't pick up. Are they asleep? Phone dead? In a tunnel? Ignoring you? You can't know — you hang up (timeout) and try again. Same ambiguity, same false-alarm risk.

5. Queueing & Network Variability

Queueing is the source of delay variability. Delays explode near capacity; noisy neighbors in multitenant clouds make them unpredictable.

Switch queues

Congestion under load — packets wait in line.

OS run queues

CPU scheduling, thread contention.

VM scheduling

Hypervisor pauses, CPU steal time.

TCP flow control

Backpressure, retransmission on loss.

Concrete data pointWhat it means
~12 network faults/monthOne medium datacenter — half isolating a machine, half a whole rack
Switch software upgradeDelayed packets over a minute
NIC driver bugDrops inbound packets while sending outbound fine — "limping" node worse than dead
🚨 "Limping" nodes — a Gigabit NIC dropping to 1 Kb/s from a driver bug is worse than a cleanly failed node. The system keeps routing traffic to a node that technically responds but is effectively useless.

Never compare a lease expiry set by a remote clock against local time-of-day — clock skew silently breaks the lease protocol.

8. Clock Skew, Drift & TrueTime

PhenomenonDataImpact
Quartz drift Google assumes 200 ppm → 6 ms drift per 30 s sync interval; 17 s/day Clocks diverge between NTP syncs
NTP over internet ~35 ms minimum error; spikes to ~1 s under congestion Cross-datacenter ordering unreliable
Leap seconds 59- or 61-second minutes Have crashed major systems — mitigate by smearing over a day
A clock reading is really a confidence interval, not a point. Spanner's TrueTime returns [earliest, latest] and waits out the interval before committing so transaction timestamps reflect causality. GPS/atomic clocks per datacenter keep uncertainty ~7 ms.

9. Timestamps Cannot Order Events

Last-write-wins (LWW) in Cassandra/Riak with time-of-day timestamps silently drops causally-later writes when the later writer's clock lags — data vanishes with no error.

Use logical clocks (Lamport timestamps, version vectors from Ch 5) for ordering. Physical clocks for human display only. Connects to Ch 5 replication LWW and Ch 7 transaction IDs.

10. Process Pauses & Stale Checks

A thread can be preempted at any point for any duration and resume without noticing — so a lease-validity check made before processing may be stale by the time the write executes.

Stop-the-world GC

Minutes have been observed — blows p99 SLA.

VM suspension

Live migration, hypervisor scheduling.

Disk I/O / paging

Synchronous I/O, page faults, thrashing.

SIGSTOP / laptop lid

Process frozen externally, resumes unaware.

🧵 Distributed systems = multithreading without shared memory. Arbitrary pauses and interleavings, but none of the tools (mutexes, atomics) translate — only messages over an unreliable network. Assume execution can stop mid-function while the rest of the world moves on.

11. Byzantine Faults

Nodes that "lie" — send arbitrary corrupted or malicious messages (Byzantine Generals Problem, Lamport).

ContextWhy Byzantine matters
AerospaceRadiation flips memory bits
Blockchain / multi-orgMutually untrusting participants
Most datacentersRightfully assume non-Byzantine — you control all nodes

BFT cost

Need >2/3 supermajority of correct nodes. Expensive protocols.

Same software

Attacker who compromises one node can likely compromise all — auth/firewalls are the real defense.

Weak lying

Still guard: checksums, input sanitization, NTP outlier rejection.

12. Mental Models

1. Truth = majority

A node cannot trust its own judgment — semi-disconnected, or waking from 1-minute GC not knowing it was declared dead. Decisions (including "is X dead?") belong to a quorum. One majority only; outvoted nodes must step down.

2. Multithreading without shared memory

Arbitrary pauses and interleavings, but no mutexes/atomics — only messages over unreliable network. Execution can stop mid-function while the world moves on.

3. Reliable from unreliable (up to a limit)

TCP over IP, error-correcting codes. Higher layer removes some fault classes (loss, duplication, reordering) but not others (delay). Know which faults your abstraction absorbs.

4. Cloud vs supercomputer

HPC: partial failure → total failure, restart from checkpoint. Internet services: tolerate failed nodes while serving. At scale, "something is always broken" — giving up is not a strategy.

14. Worked Example: Fencing Tokens

Scenario: a file in a storage service must be written by one client at a time, enforced by leases from a lock service (HBase actually had this bug).

The bug: lease + GC pause

1. Client 1 acquires lease for file F
2. Client 1 hits stop-the-world GC pause longer than lease TTL
3. Lease expires; Client 2 acquires lease and writes to F
4. Client 1 wakes, still believes lease valid (nothing told the paused thread)
5. Client 1 writes too → writes clash and corrupt F

Client-side lease checking CANNOT fix this:
  check_lease()  // passes — lease was valid when checked
  [GC PAUSE — lease expires, Client 2 writes]
  write_to_file()  // stale check — corruption

The fix: server-side fencing tokens

Lock service returns a fencing token with every grant —
  a number that increases monotonically (ZooKeeper zxid or cversion).

Every write must carry its token.
Storage service checks and rejects any write whose token ≤ last processed.

Timeline:
  Client 1 gets token 33, then GC pauses
  Client 2 gets token 34, writes (storage records max=34) ✓
  Client 1 wakes, writes with token 33 → REJECTED (33 < 34) ✓

Required properties:
  Safety: uniqueness + monotonic sequence (must NEVER break)
  Liveness: availability (lock service keeps granting tokens)
Key insight: The resource (storage) takes an active role in enforcement. Client-side lease checks are always stale-able. Fencing provides safety (uniqueness + monotonicity); lock service availability is liveness.

17. Key Takeaways

  1. Partial failure is the defining property of distributed systems: operations non-deterministically fail, go slow, or vanish — and you may never learn whether they succeeded.
  2. No response tells you nothing about why; timeouts are the only failure detector and they conflate node death with network trouble.
  3. Never use time-of-day clocks for elapsed time or event ordering; monotonic clocks for durations, logical clocks for ordering, and treat any wall-clock reading as a confidence interval.
  4. Any thread can pause arbitrarily long at any point (GC, VM suspend, paging) and resume unaware — protect resources server-side with fencing tokens, not client-side lease checks.
  5. A node's self-assessment is worthless; truth is a quorum decision, and outvoted nodes must step down.
  6. Design against an explicit system model (usually partially synchronous + crash-recovery); require safety always, liveness conditionally.
  7. If you can stay on a single machine, do — distribution is justified by fault tolerance and latency (data near users), not fashion; bounded-delay networks require utilization/cost most systems won't pay.

18. Junior SWE Checkpoints

Q1: Why can't you tell why a request got no response?

Request lost, queued, server crashed, server paused (GC), response lost, or response delayed — all look identical (silence). Timeouts are a guess that conflates node failure with network trouble.

Q2: Time-of-day vs monotonic clock — when to use each?

Time-of-day (wall clock): human timestamps, log correlation — but can jump backward (NTP). Monotonic (nanoTime): timeouts and durations — always forward, but meaningless across machines. Never use wall clock for elapsed time or cross-node ordering.

Q3: Why does LWW with timestamps silently lose data?

Later writer's clock may lag earlier writer's. LWW picks higher timestamp, discarding the causally-later write — no error, no conflict surfaced. Fix: logical clocks (version vectors, Lamport timestamps).

Q4: Client checks lease valid, then writes. Why can this still corrupt data?

GC pause (or VM suspend) between check and write. Lease expires; another client acquires and writes. First client wakes, check was stale. Fix: fencing tokens checked by the storage service, not the client.

Q5: Safety vs liveness — give an example of each.

Safety ("nothing bad"): fencing token uniqueness — must never break, even if all nodes crash. Liveness ("eventually good"): availability, eventual consistency — conditional on majority up and network recovery.

Q6: Why do most datacenters assume crash-recovery, not Byzantine?

You control all nodes; same software everywhere — compromise one, likely compromise all. BFT needs >2/3 honest nodes and expensive protocols. Real defense: auth, access control, firewalls. Still guard weak lying with checksums and NTP outlier rejection.

Q7: How does this chapter connect to Ch 9 consensus?

Ch 8 motivates the problem (partial failure, unreliable components) and the system model (partially sync + crash-recovery). Ch 9 delivers the algorithms — quorums, Raft/Paxos, leader election — that provide safety and liveness guarantees within that model. Fencing tokens underpin Ch 9's leader-election examples.
