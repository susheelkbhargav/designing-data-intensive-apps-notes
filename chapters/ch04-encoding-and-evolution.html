1. Core Idea

Code changes roll out gradually — rolling upgrades server-side, laggard clients elsewhere — so old and new code, and old and new data formats, coexist in one running system. Everything hinges on two compatibility properties:

Backward compatibility

Newer code reads data written by older code. Easy — you know the old format.

Forward compatibility

Older code reads data written by newer code. Harder — old code must ignore additions it doesn't understand.

Choose an encoding whose schema evolution rules give you both, and you can deploy any component in any order without downtime.

2. Framework: Thrift / Protocol Buffers

Schema-driven binary encodings with numeric tag numbers. Internal service-to-service data (RPC, storage) in statically typed shops; compact encoding plus codegen.

WhenInternal RPC/storage; statically typed services; you want compact wire format + codegen.
HowSchema (IDL) assigns each field a tag number. Encoded record = concatenation of (tag, type, value) — no field names on the wire.
Why it worksTags are stable aliases for names — rename freely, wire never sees names. Old code skips unknown tags (type tells it how many bytes to skip) → forward compatible. New code still understands old tags → backward compatible.
Failure modeReuse or change a tag number → all existing data silently misinterpreted. Add a required field after v1 → new code fails reading old data. Removed tags are burned forever.
required string userName = 1;
optional int64 favorite_number = 2;
repeated string interests = 3;
Real systems: gRPC on Protobuf (Google, most microservices), Apache Thrift (Facebook origin), Finagle/Thrift stacks, Rest.li with Protobuf payloads.

3. Framework: Avro

Schema-driven binary encoding with no tags — just values concatenated. Most compact of all for the same record.

WhenHadoop-style big files of records; dynamically generated schemas (e.g., dumping a relational DB — column names become field names automatically).
HowDecoder resolves writer's schema (what encoder used) against reader's schema (what decoder expects). They need only be compatible, not identical: fields matched by name, extra writer fields ignored, missing ones filled from reader's default.
Why it worksNo tag bookkeeping — friction-free for program-generated schemas. Same Person record: 32 bytes (vs 33 Protobuf, 59 Thrift Binary, 34 Thrift Compact).
Failure modeReader must obtain writer's schema somehow — object container file header, schema registry (Espresso), or connection negotiation (Avro RPC). Lose that and bytes are unreadable. Fields without defaults break compatibility on add (backward) or remove (forward).
Tags vs names is the Protobuf/Avro fork. Tags = wire stability with manual bookkeeping. Name-matching = friction-free dynamically generated schemas. Pick by whether a human or a program authors your schemas.

4. Backward & Forward Compatibility

ChangeProtobuf / ThriftAvroJSON
Add field New tag, must be optional/defaulted. Old readers skip tag (forward ✓). New readers tolerate absence (backward ✓). Add with default value. Old readers ignore; new readers fill default on old data. Just works if readers ignore extras — but nothing enforces it.
Remove field Only if optional; never reuse the tag. Only if field had a default — else forward compat breaks. Readers may break on missing fields.
Rename field Free — names aren't on the wire. Reader-schema aliases: backward but not forward compatible. Breaks unless both sides agree.
Change datatype Risky — int32→int64 truncates when old code reads new data. repeated trick for optional scalar→list. Resolution rules per Avro spec. Number ambiguity (int vs float, JS 2^53 limit).
Decode → model object → re-encode drops unknown fields (Figure 4-7). Old code reads a record, updates it, writes it back — silently deleting fields newer code wrote. Preserve unknown fields at the application level. Same trap when a consumer re-publishes messages.

5. Key Concepts

Encoding formats compared

FormatProsCons
Language-built-in (Java Serializable, pickle) Convenient Language-locked, security hole (RCE on decode), versioning-hostile, inefficient. Transient use only.
JSON / XML / CSV Cross-org interchange, human-readable Number ambiguity, no binary strings (Base64), optional schemas. Twitter ships 64-bit IDs as strings (JS float corrupts > 2^53).
Binary JSON (MessagePack) Modest savings (81→66 bytes) Field names still ride along — schema-driven formats win by omitting names.
Thrift / Protobuf / Avro Compact, schema-as-docs, pre-deploy compat checks, codegen Schema management overhead; Avro needs schema delivery channel.
Schema evolution = schema-on-read flexibility with schema-on-write guarantees. Databases fake single-schema appearance — add nullable column, fill nulls on read — while old rows keep their original encoding forever.

Merits of schemas

  • Compactness — omit field names from every record.
  • Documentation — schema is guaranteed-current contract.
  • Compatibility checks — verify forward/backward before deploying.
  • Codegen — static typing from IDL.

6. Dataflow Modes

Who encodes, who decodes — compatibility responsibilities differ by mode:

Services: servers first, clients second. Backward compatibility on requests (old server reads new client fields? No — new server reads old client). Forward compatibility on responses (old client reads new server response).

7. RPC Flaws & Modern Alternatives

RPC fakes local calls ("location transparency") but networks add realities code can't ignore:

Network realityWhy RPC hides it at your peril
Timeouts with unknown outcomeRequest may have succeeded — retry needs idempotence keys.
Wild latency varianceLocal call assumptions break; need futures/async.
No pass-by-referenceLarge objects must be copied or referenced by ID.
RetriesWithout idempotence, duplicate side effects.

Modern RPC

gRPC on Protobuf, Finagle/Thrift, Rest.li — embrace the network with futures and streams. Dominates intra-datacenter.

REST for public APIs

curl-debuggable, no codegen required. Predominant for cross-org boundaries.

Dead RPC frameworks: CORBA, EJB/RMI, DCOM — no compatibility story. SOAP/WSDL: codegen-dependent, interop-hostile. Distributed actor frameworks on default Java serialization (Akka default) break rolling upgrades — swap in Protobuf.

8. Mental Models

1. Data outlives code

Replace all running code in minutes; five-year-old rows sit in original encoding forever. Migrations are expensive — schema evolution makes the DB appear single-schema.

2. Writing to DB = message to future self

Backward compatibility non-negotiable. Forward too — during rolling upgrade, old readers see new writers' data.

3. Tags vs names fork

Protobuf: manual tag bookkeeping, wire-stable renames. Avro: name-matching, program-generated schemas. Pick by schema author.

4. Servers first, clients second

Service deployment assumption → backward-compatible requests, forward-compatible responses.

13. Key Takeaways

  1. Rolling upgrades force coexistence — design every encoding for backward AND forward compatibility from day one.
  2. Schema-driven binary formats (Thrift/Protobuf/Avro) beat schemaless JSON internally: smaller, self-documenting, compatibility checkable pre-deploy.
  3. Decision criteria: cross-org interchange → JSON/REST; internal static-typed services → Protobuf/gRPC or Thrift; dynamically generated schemas and big analytic files → Avro.
  4. Tag numbers are forever: never reuse, never make post-v1 fields required; in Avro, always give evolvable fields defaults.
  5. Compatibility differs by dataflow mode: databases need both directions; services need backward-compatible requests, forward-compatible responses; brokers need both to deploy in any order.
  6. Don't let RPC pretend the network isn't there — retries need idempotence, timeouts mean unknown outcome.

14. Junior SWE Checkpoints

Q1: What's the difference between backward and forward compatibility?

Backward: newer code reads old data (you know the old format). Forward: older code reads new data (old code must skip/ignore unknown fields). Both needed during rolling upgrades.

Q2: Why is Protobuf 33 bytes but JSON 81 for the same record?

Protobuf puts tag+type+value on the wire — field names live only in the schema. JSON repeats field names in every record. MessagePack (66 bytes) still carries names.

Q3: You add a required field to a Protobuf schema after v1 is in production. What breaks?

New code reading old data without that field fails. Every post-v1 field must be optional or have a default. Required fields are only safe at initial deployment.

Q4: How does Avro decode bytes with no tags on the wire?

Reader resolves writer's schema against reader's schema (matched by field name). Reader must obtain writer schema via file header, schema registry, or RPC handshake. Without it, bytes are meaningless.

Q5: A service deploys new server before clients update. What compat do you need on requests vs responses?

Requests: backward compatible — new server must read old client requests. Responses: forward compatible — old clients must read new server responses (skip unknown fields).

Q6: Why shouldn't old code decode a record to a model object and re-encode it?

Unknown fields get dropped silently — deleting data newer code wrote (Figure 4-7). Same trap when a Kafka consumer re-publishes messages. Preserve unknown fields at application level.

Q7: Why does Twitter ship tweet IDs as JSON strings?

JavaScript numbers are IEEE 754 floats — integers above 2^53 lose precision. 64-bit IDs must be strings for JS consumers.
