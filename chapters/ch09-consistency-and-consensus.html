1. Core Idea

The best way to build fault-tolerant distributed systems is to find general-purpose abstractions with useful guarantees, implement them once, and let applications rely on them — the same move transactions made for single-node faults.

🎯 Key abstraction

Consensus — getting all nodes to agree on something.

📶 The ladder

Linearizability → causal ordering → total order broadcast → consensus.

🔗 Equivalence

The top rungs are all the same problem in disguise.

Climb the ladder: start with the strongest single-object guarantee (linearizability), discover cheaper middle ground (causal consistency), then realize total order broadcast and consensus are equivalent — solve one, you've solved leader election, atomic commit, locks, uniqueness constraints, and linearizable compare-and-set.

2. Framework: Linearizability

Also: atomic consistency, strong consistency, immediate consistency. The strongest single-object guarantee.

WhenLocking/leader election, uniqueness constraints (usernames, seat booking), cross-channel timing dependencies (message queue racing a file store).
HowMake the system appear as if there is only a single copy of the data and all operations are atomic. Once any client reads a new value, all subsequent reads (by any client) must return it — a recency guarantee.
Why it worksEvery operation takes effect atomically at some point between its start and end → one timeline all clients agree on.
Failure modeExpensive. Single-leader is only potentially linearizable; multi-leader is not; Dynamo-style quorums (w+r>n) are not — concurrent readers can still see old and new values. Attiya & Welch: linearizable response times are inevitably high in variable-delay networks. Even multicore RAM isn't linearizable.

What is (and isn't) linearizable

SystemLinearizable?Why
Single-leader + sync follower readsPotentially ✓Leader serializes writes; sync replication + leader reads
Single-leader + follower reads✗Lagging followers return stale values
Multi-leader✗Concurrent writes on different leaders
Leaderless quorum (w+r>n)✗Concurrent readers can see old and new values simultaneously
Consensus-backed (Raft/ZK)✓Majority quorums + single leader per epoch
Real systems: etcd, ZooKeeper (linearizable reads via sync), Spanner (TrueTime-bounded staleness), FoundationDB (strict serializability). Most "strong consistency" claims need scrutiny — ask which operations and under what failure model.

3. Framework: Two-Phase Commit (2PC)

Also: XA transactions, distributed atomic commit. Used for atomic commit across multiple nodes/partitions or heterogeneous systems.

WhenMultiple services/databases must commit or abort together despite no shared transaction manager.
HowA coordinator (transaction manager) sends prepare to all participants. Each replies yes only if it can definitely commit (writes durably, surrenders abort right). If all yes → coordinator writes decision to its log (the true commit point), then sends commit/abort.
Why it worksParticipants can't unilaterally decide; coordinator's log is the single source of truth for the outcome.
Failure modeBlocking. Coordinator crash after prepare leaves participants in doubt — they hold locks until coordinator recovers. Safety but not termination. Not fault-tolerant consensus.
2PC ≠ consensus. It provides safety (atomicity) but not termination (liveness). A crashed coordinator blocks everything. Fault-tolerant consensus (Raft/Paxos) adds majority quorums and epochs to guarantee progress.

4. Linearizability vs. Serializability

Interview-sharp distinction. These sound similar but operate at different layers.

LinearizabilitySerializability
ScopeSingle object ("register")Multi-object transactions
GuaranteeRecency — reads see latest writeTransactions behave as if executed in some serial order
Transactions?No — individual reads/writesYes — isolation property
Cross-object orderingNoneYes — serial order across all objects in txn
Example systemsZooKeeper CAS, etcdPostgreSQL SERIALIZABLE, FoundationDB
Both together = strict serializability (strong-1SR). 2PL-based serializability is typically linearizable. SSI is serializable but NOT linearizable — it reads from a consistent snapshot, which is stale by design (Ch 7).

5. CAP Theorem & Kleppmann's Critique

C — Consistent

Linearizability: all nodes see the same data at the same time.

A — Available

Every request gets a response (not an error), even if it's stale.

P — Partition-tolerant

System continues despite network partitions between nodes.

CAP claim: during a network partition you choose linearizability or availability — not both.

Kleppmann's critique — CAP is mostly of historical interest:
  • Considers one consistency model (linearizability) and one fault (partitions)
  • Says nothing about delays, crashes, or trade-offs in normal operation
  • CP/AP labels mislead — many real systems are neither cleanly CP nor AP
  • Avoid CAP for precise reasoning; use specific guarantees instead

6. Causal Consistency

The strongest consistency model that doesn't lose availability under partitions.

PropertyDetail
Partial orderCausality gives a partial order — concurrent ops are incomparable
vs linearizabilityLinearizability implies causality (total order). Causal is weaker and cheaper.
Practical sweet spotMany apps that "need" linearizability actually only need causal consistency
📱 Social media: You post a comment, then your friend replies. Causal consistency ensures everyone sees your post before the reply. But two strangers posting simultaneously don't need a global order — that's overkill (and expensive).

7. Lamport Timestamps vs. Version Vectors

Two different tools for ordering — don't confuse them.

Lamport TimestampVersion Vector
Format(counter, node ID)One counter per replica per key
OrderingTotal order consistent with causalityDetects concurrent vs causally ordered
Concurrency detection✗ Cannot tell if two ops are concurrent✓ Explicitly identifies concurrent writes
SizeCompact (2 numbers)Grows with replica count
Uniqueness constraints✗ Winner only known after collecting all ops✓ Can detect conflicts at write time
Don't use Lamport clocks for uniqueness constraints. Two clients can both "claim" a username with concurrent Lamport timestamps — the winner is only final after collecting all operations. Use consensus (compare-and-set on a log) instead.

8. Total Order Broadcast

Messages delivered reliably, in the same order, to all nodes — the order is fixed at delivery time (stronger than timestamp ordering).

PropertyDetail
Reliable deliveryEvery message delivered to every node (no loss)
Total orderAll nodes see messages in the identical sequence
Same asA replication log (Ch 5 single-leader)
Equivalent toConsensus — linearizable CAS ↔ total order broadcast
Consensus reductions: linearizable compare-and-set, atomic commit, total order broadcast, locks/leases, uniqueness constraints, and leader election are all reducible to consensus. Solve one, you've solved them all.

9. FLP Impossibility Result

Fischer, Lynch, Paterson (1985): consensus is impossible with a deterministic algorithm in the asynchronous model if a node may crash.

AssumptionImplication
Asynchronous networkNo bound on message delay — can't distinguish slow from dead
Deterministic algorithmSame inputs → same outputs, always
One crash allowedEven a single faulty node makes consensus impossible
Great theoretical importance, limited practical restriction. FLP tells us pure async consensus can't exist — but adding timeouts or randomness (Raft election timeouts, Paxos randomized proposers) makes it solvable. Every production consensus system "cheats" on the async model.

10. Fault-Tolerant Consensus: Raft, Paxos & Friends

What 2PC lacks: termination — the liveness property that guarantees progress even when nodes fail.

Consensus properties

PropertyMeaning
Uniform agreementAll non-faulty nodes decide the same value
IntegrityNo node decides twice, and decided value was proposed
ValidityIf everyone proposes the same value, that's what's decided
TerminationEvery non-faulty node eventually decides (2PC lacks this!)

Algorithms

AlgorithmNotesUsed by
Viewstamped Replication (VSR)View numbers = epochsResearch predecessor
PaxosSingle-value; Multi-Paxos for sequencesChubby (Google), historical
RaftDesigned for understandability; leader + log replicationetcd, CockroachDB, TiKV, Consul
ZabSimilar to Raft; total order broadcastZooKeeper
Most consensus algorithms decide a sequence of values — they implement total order broadcast directly. Don't implement consensus yourself: use ZooKeeper, etcd, or a database with built-in Raft.

11. Epochs and Quorums

Resolves the chicken-and-egg: consensus uses a leader, but electing a leader needs consensus.

ConceptDetail
Epoch numberMonotonically increasing per leader election (ballot in Paxos, view in VSR, term in Raft)
Leader confirmationLeader must get quorum to confirm no higher-epoch leader exists before deciding
Two quorumsElection quorum + proposal quorum — overlapping quorums prevent split brain
Fencing tokens: A lock alone doesn't guarantee uniqueness — a paused (GC) old leader can wake and corrupt data. Use monotonic fencing tokens (ZooKeeper zxid) so downstream services reject stale leaders' requests.

12. ZooKeeper & etcd

Consensus outsourced. Don't roll your own — use a coordination service.

FeatureWhat it providesUse case
Linearizable CASCompare-and-set with monotonic zxid fencing tokensLocks, leases, uniqueness
Ephemeral nodesAuto-deleted when session expiresLeader election, liveness detection
Change notificationsWatch for data changes (no polling)Service discovery, config updates
Sequential nodesMonotonic sequence numbersQueue, lock ordering
Exactly-once message processing: atomically commit message acknowledgment + database writes (heterogeneous transaction via 2PC or idempotent consumer) → message is effectively processed exactly once, even with retries. Returns in Ch 11 stream processing.

13. Mental Models

1. Single-copy illusion

Linearizability = "behave as though there is only one copy of the data and all operations are atomic." Everything about its cost follows from maintaining that illusion across replicas.

2. Consensus reductions

Linearizable CAS, atomic commit, total order broadcast, locks/leases, uniqueness constraints, and leader election are all reducible to consensus. Solve one, you've solved them all. This is why ZooKeeper sits under half the infrastructure you use.

3. Leader per epoch, not forever

Consensus uses a leader, but electing a leader needs consensus — not a contradiction. Escape via epoch numbers: you don't need a unique leader forever, only a unique leader per epoch.

15. Worked Example: 2PC Coordinator Crash

Setup

App completes writes on databases 1 and 2, then the coordinator runs phase 1: prepare to both. Both vote "yes" — each has durably written the transaction and irrevocably promised to commit if told to.

Why DB 1 is stuck

✗
Can't unilaterally abort — DB 2 may have committed; unilateral abort breaks atomicity
✗
Can't unilaterally commit — maybe another participant voted no
✗
Can't ask DB 2 safely — doesn't know the coordinator's decision
✓
Only way forward: wait for coordinator to recover and read its decision from the transaction log — the commit point of 2PC is really a single-node atomic commit on the coordinator
Meanwhile: the in-doubt participant holds its locks, blocking every other transaction touching those rows. This is why 2PC is a blocking protocol. 3PC "fixes" it only by assuming bounded delays and a perfect failure detector — which real networks don't provide.

Bonus: Linearizability violation

Alice and Bob check the 2014 World Cup final score. Alice refreshes, sees the result, exclaims it. Bob then refreshes and gets a stale "game in progress" from a lagging replica. Because Bob's query started after Alice's completed (via a side channel — her voice), returning the older value violates linearizability's recency guarantee.

18. Key Takeaways

  1. Linearizability = recency on a single object; serializability = serial-order illusion for multi-object transactions. Know the distinction cold; combined they're strict serializability.
  2. Wide swaths of coordination — leader election, atomic commit, locks, uniqueness, total order broadcast, linearizable CAS — are all equivalent to consensus.
  3. 2PC gives atomic commit but blocks on coordinator failure; fault-tolerant consensus (Paxos/Raft/Zab/VSR) adds termination via majority quorums and epochs.
  4. Causal consistency is the practical middle ground: preserves what users perceive as "order" without linearizability's latency and availability cost.
  5. FLP says consensus is impossible in the pure asynchronous model — timeouts and randomness rescue it in practice.
  6. Don't implement consensus yourself: use ZooKeeper/etcd, and use fencing tokens with any lock or lease.
  7. If your system has a leader and can't tolerate its loss, you either wait, pick manually (failover), or run a consensus algorithm — and consensus needs a majority alive.

19. Junior SWE Checkpoints

Q1: What's the difference between linearizability and serializability?

Linearizability = recency guarantee on a single object (register). Serializability = isolation property on multi-object transactions (some serial order). Both together = strict serializability. SSI is serializable but NOT linearizable.

Q2: Does w+r>n quorum replication give linearizability?

No. Concurrent readers can still see old and new values. Overlap guarantees freshness for completed writes, not a single-copy illusion. Need consensus (Raft/ZK) for linearizability.

Q3: 2PC coordinator crashes after all participants vote yes but before sending commit to DB 1. What happens?

DB 1 is in doubt — can't abort (DB 2 may have committed), can't commit (maybe someone voted no). Holds locks, blocks other transactions. Must wait for coordinator recovery. This is why 2PC is blocking and not fault-tolerant consensus.

Q4: Why can't you use Lamport timestamps for username uniqueness?

Lamport gives a total order but can't detect concurrency. Two clients can both "claim" a username with concurrent timestamps — winner only known after collecting all operations. Use consensus CAS on a log instead.

Q5: What problem does FLP prove, and why doesn't it stop us?

Consensus impossible with deterministic algorithms in pure async model (one crash). We cheat with timeouts (partial synchrony) and randomness (Raft election timeouts). Great theory, limited practical impact.

Q6: Why do you need fencing tokens with distributed locks?

A paused (GC) old leader can wake after a new leader is elected. Without fencing, both write — data corruption. Fencing token (monotonic zxid) lets downstream services reject stale leader's requests.

Q7: What's equivalent to consensus?

Linearizable CAS, atomic commit, total order broadcast, locks/leases, uniqueness constraints, leader election — all reducible to each other. Solve one, solve them all. This is why ZooKeeper/etcd underpin so much infrastructure.
